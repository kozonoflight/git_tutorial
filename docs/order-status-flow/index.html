EC-RIDER

注文ステータスと業務フロー

元の図は、顧客・ステータス・運営・EDI・基幹・WMS を横に並べ、そのあいだを線でつないでいる。ここでは線を追わずに読めるように、ステータス遷移、業務、システム連携、メールを分けてある。

通常の流れ ステータス遷移 業務 システム連携 メール キャンセル・返品・差戻し 図から読み取れないこと

4つの色

同じできごとを、見る観点で分けている。黄がステータス、青が業務、紫がシステム連携、緑がメール。

ステータス 業務 システム連携 メール キャンセル・返品 差戻し 利用しない
キャンセルの単位は配送（基幹オーダー）。返品依頼の単位は注文明細。入金待ちと、説明欄にある「出荷指示」は使わない。WMS の列は見出しだけで、箱も線もない。

0注文をつくる

業務

  • 顧客がフロントサイトで新規注文する。
  • 運営が管理サイトで代理注文する。進み方は、その注文に使ったフロントユーザの承認権限に従う。
  • EDI から新規注文データを受け取って注文を作る。

システム連携

EDI から EC-Rider へ新規注文データが渡る。顧客と運営の注文作成は EC-Rider の中で完結する。

メール

この瞬間には送らない。入ったステータスのメールを見る。

入るステータス

  • 承認権限がない → 承認待ち
  • 承認権限がある → 受注待ち（図の赤線）
  • EDI の新規注文 → 受注待ち（図の赤線。承認待ちへの線はない）
1承認待ち

業務

承認権限を持たないフロントユーザの注文が、承認を待っている。

  • 同一販売組織の、承認権限を持つ顧客が注文承認する。
  • 運営が代理承認する。
  • リクエスト注文だけ、運営が承認依頼する。ステータスは承認待ちのまま。

システム連携

基幹へはまだ渡さない。

メール

注文承認依頼メール。宛先は店舗の承認者。

次

承認すると受注待ち。キャンセルは下の節。

2受注待ち

業務

運営の受付待ち。外部サプライヤー商品で受注確認区分があるときは、確認を取る状態でもある。注文金額を変えられるのはここだけ。

  • 運営が注文変更する。変えても受注待ちのまま。
  • 基幹が与信を確認する。

システム連携

  • EC-Rider から基幹へ、30分間隔で注文を連携し、受注扱いとする。
  • 与信上限内なら、基幹オーダー番号が返る。EC が取り込むと出荷待ち。

メール

図では次の3通が、受注待ちから1本の線でまとまっている。箱は顧客レーンにある。

  • 注文受付メール
  • 注文承認完了メール
  • 注文内容変更通知メール

次

与信回答の取込で出荷待ち。与信が上限に達したあとは、図にも説明にも書かれていない。

3出荷待ち

業務

納期回答を待っている。顧客と運営の追加操作は、キャンセルと差戻し以外は図にない。

システム連携

在庫があれば基幹からピック番号が返る。EC が取り込むと出荷指示済み。与信回答と納期回答は同じタイミングになることがある。

メール

なし。入金確認メールは出荷待ちから線が出ているが、利用しない。

次

納期回答の取込で出荷指示済み。差戻すと受注待ち。

4出荷指示済み

業務

納期回答済み。商品の出荷準備をする。準備の担当レーンは図にない。出荷そのものは基幹が、納品予定日に合わせて行う。

システム連携

基幹から出荷実績が返る。EC が取り込むと出荷済み。

メール

納期回答メール。出荷指示済みから顧客レーンへ線が出ている。説明文は、納期回答の取込時に送る、とある。

次

出荷実績の取込で出荷済み。差戻すと出荷待ち。顧客のキャンセル依頼はここまで届かない。運営のキャンセルはできる。

5出荷済み

業務

出荷が終わっている。顧客も運営も、注文明細ごとに返品依頼できる。説明文は出荷済み以降。

システム連携

出荷実績を取り込んだ結果がこのステータス。ここから新たに渡すデータは図にない。

メール

  • 出荷完了メール。説明文の宛先は注文者。
  • 出荷完了メール（店舗宛て）。

次

返品依頼で返品依頼中。

キャンセル、返品、差戻し

キャンセル

顧客が依頼する経路と、運営が直接完了させる経路は別。

承認待ち
受注待ち
出荷待ち顧客が依頼できる
キャンセル依頼 →
キャンセル依頼中注文キャンセル依頼メール
連携前なら →
キャンセル完了注文キャンセル完了メール
すでに基幹へ連携済みなら、キャンセル依頼を基幹へ渡す。基幹のキャンセルデータを取り込んでキャンセル完了になる。不能と返ったあとは図にない。
運営は、承認待ち、受注待ち、出荷待ち、出荷指示済みからキャンセルでき、キャンセル依頼中を経由せずキャンセル完了へ進む。出荷指示済みでキャンセルできるのは運営だけ。図のこの線は基幹を経由していない。説明文は、基幹からキャンセルデータが返って取り込み完了する、とも書いている。

返品

出荷済み
顧客または運営が明細単位で依頼 →
返品依頼中返品依頼メール（注文者）
基幹が返品 →
返品完了返品完了メール（注文者）

基幹が処理するのは、商品が本社へ返送され、返品できる場合。返品依頼を基幹へ送る線は図にない。返ってくるのは返品実績。

差戻し

運営が戻せるのはこの4つだけ。戻したあとに別のメールが描かれているわけではない。

いま戻った先
出荷指示済み→出荷待ち
出荷待ち→受注待ち
キャンセル依頼中→出荷待ち
返品依頼中→出荷済み

キャンセル依頼中の差戻しは、依頼する前のステータスへ戻す線ではない。行き先は出荷待ちに固定されている。

対象内容
与信が上限に達したとき上限内なら出荷待ち、とだけある。達したあとのステータスはない。
キャンセル不能基幹が不能を返したあとのステータスはない。
返品不可返品できる場合の処理だけが書かれている。

入金入金待ち、入金、入金確認、入金確認メールは利用しない。入金確認から出荷待ちへ進む線だけある。
基幹の楕円「与信回答」「納期回答」「注文変更」が1つの楕円に入っている。矢印の先は出荷待ちだけ。納期回答で出荷指示済みになることと、注文変更が受注待ちの運営操作であることは、別の線と説明文の側に書かれている。
運営キャンセルの経路図は基幹を経由せずキャンセル完了へ直結する。説明文は基幹からのキャンセルデータ取込で完了する、と書いている。
