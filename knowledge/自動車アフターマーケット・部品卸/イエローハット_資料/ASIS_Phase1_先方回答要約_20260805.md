## 一言でいうと

**BtoBの配送出荷は倉庫（物流部指示）。店舗からは出荷しない。**  
ただし **入荷は倉庫／各店舗で都度行い、倉庫在庫システム・POS → 基幹へ集約**。  
交換作業が絡む案件では **店舗在庫を使う**（＝店舗は「出荷拠点」ではなく「作業時の在庫拠点」）。

## 出荷元の読み方（重要）

先方文言:

> 店舗からは出荷はしません、交換作業が絡むものは基本店舗在庫使用、なので近いのは①です。

解釈:

```
BtoB「配送」出荷  …… 倉庫（物流部指示）。店舗からは出さない
交換・取付が絡む …… 店舗在庫を使う（作業用）
入荷             …… 倉庫／各店舗で都度。倉庫在庫システム・POS → 基幹集約
```

→ ユーザー理解（**店舗出荷なし／入荷は店舗・倉庫で都度→基幹集約**）は正しい。  
加えて「店舗在庫ゼロ」ではなく、**作業絡みでは店舗在庫を使う**点が残る。

## Phase1設計への効きどころ

1. **出荷拠点は倉庫中心**（店舗を配送出荷元にしない）  
2. **店舗在庫は見せる／作業連動用**の可能性（配送引当先ではない）  
3. **入荷は現場起点・都度**（倉庫システム／POS → 基幹集約）で仮説どおり  
4. **出荷指示は物流部アナログ**がボトルネック。EC化しても指示・ステータスの置き場が論点  
5. **商品の自動連携はPOSのみ**。倉庫・適合は別設計が必要  
6. **予約に顧客なし** → Phase2で顧客キーの設計が要る  
7. **取寄せはEC要件としてYES**（フロント欠品→取寄せ、管理でメーカー指示）  
8. **領収書不要／掛け売り前提**の帳票設計

## 8/7整理（社内で仮置き・解釈済み）

| 項目 | 整理結果 |
|------|----------|
| 物流部のアナログ指示手段 | **メール・電話と仮置き**（詳細は打合せで補足） |
| 「売上計上」の意味 | **出荷実績登録**（在庫を減らし出荷完了とする）と整理 |
| 仕入データの到着先 | **各店舗・倉庫**。「入荷場所で承認」＝POS／倉庫システムでの**入荷入力**と解釈 |
| 適合・倉庫への商品マスタ反映 | 自動連携はPOSのみ（YH回答）→ **CSVまたは画面入力**と整理 |

## 8/7整理②：「数量管理のみ／売上計上」の読み解き

回答原文「倉庫在庫のシステムで数量管理のみ行い、卸先、店舗POSへの売上計上」の解釈。

| 処理 | 場所 | 中身 |
|------|------|------|
| 引当 | 基幹が正 → 倉庫・POSへ連携 | **数量の予約**として飛ぶ |
| 出荷実績 | 倉庫在庫システム | **数量の減算**（金額は扱わない） |
| 売上計上（卸先分） | **基幹**（ほぼ確実。掛売り・請求は基幹。要一言確認） | 出荷基準で売上 |
| 売上計上（店舗利用分） | **店舗POS** | POS売上計上と同時に店舗在庫減 |

- 「数量管理のみ」＝**金額・売上を扱わない**の意。引当（数量予約）が飛ぶことと**矛盾しない**。
- 在庫が落ちるタイミングは二系統：倉庫出荷分＝出荷実績登録／店舗利用分＝POS売上計上。

## 新カート（EC-Rider）の方針（8/7確定版）

```
取引先 → フロントで注文（または担当者が代理注文）
 → EC受注 → 受注連携バッチ（CSV）→ 基幹 受注取込・在庫引当
 → 物流部：注文受付メール受領 → 管理サイトからボタン1つで出荷指示
 → 倉庫：出荷
 → 基幹：売上計上（出荷実績登録）＝注文完了
 → 出荷実績CSV → EC受注連携バッチ → 「出荷済み」＋出荷完了メール
 → 倉庫在庫システム：手で在庫減算（現行のまま）
```

| 論点 | 決定 |
|------|------|
| 出荷指示の主体 | **物流部が管理サイトから実行**（アナログ→ボタン1つ。改善の目玉） |
| ECの「出荷済み」トリガー | **基幹の売上計上（出荷実績登録）＝注文完了**。ステータス二重管理を避ける |
| 倉庫在庫システムの在庫減算 | **手作業のまま**。基幹出荷実績登録との自動連携は**ペンディング**（Phase1スコープ外候補） |
| 売上・請求 | 基幹に残す（掛売り・出荷基準のまま） |
| 店舗POS | **通常卸フローには登場させない**。入荷入力／（要判断）店舗在庫表示／（★未回答）タイヤ着脱時の消費のみ |
| タイヤ交換 | 通常卸ルートに描かない。★本丸の回答が来るまで別パターン（要確認）扱い |

## Phase2の構造仮説（8/7・店舗POSの居場所）

店舗POSの登場場面は**Phase2（作業送客）に完全分離**される、が現時点の仮説。

```
取引先 → 取扱店舗の在庫をリアルタイム閲覧（POS在庫→基幹→EC）
 → 交換予約・作業依頼を発注
 → 予約情報の管理（ピット空き枠×日時）
 → 店舗で作業実施
 → 完了時：基幹に売上登録 ＋ 店舗在庫はきだし（POSで在庫減）
```

| 論点 | 内容 |
|------|------|
| 予約システム | **新規で作るより既存PIT予約と「つなぐ」が先**（設計書No.7・保管資料の既存PIT作業予約API）。予約側は顧客情報なし→取引先・依頼情報はBtoB側が保持し、キーで紐づけ |
| 売上二重計上 | 「基幹の卸先請求（掛売り）」と「POS売上（在庫はきだし）」の関係整理が設計論点。POSは基幹自動連携のため、どちらを正にするか |
| 同時引当 | **店舗在庫×ピット空き枠の同時引当**がPhase2の肝＝カスタムの中心。「ピットを在庫のように扱う」夢ポイントに直結 |

→ Phase1＝倉庫配送の物販／Phase2＝店舗在庫×ピットの作業予約、で店舗POSの居場所が分離。

## マスタ連携方針（8/9更新・YH方針確定）

**商品・在庫は基幹から自動連携。サプライヤー・顧客は基幹で増えたらECにも登録（手動）。**

| マスタ | 方針 | 備考 |
|--------|------|------|
| 商品 | **基幹から自動連携（定間隔）** | YH方針として確定（8/9）。※8/7に「CSV一括で足りるのでは」と社内たたきを出したが、これはローリングス基幹直プランの前例に引っ張られた案。YH要件に手動の根拠はなく、自動連携で進める |
| 在庫 | **自動連携（定間隔）** | 欠品・納期表示が本丸。廃番も在庫0で自然にカバーされる |
| 価格 | 基幹からの連携に含めて反映 | 改定日に確実反映されるよう連携タイミングを設計 |
| サプライヤー | 基幹で増えたらECにも登録（手動） | 件数が少なく頻度も低い |
| 顧客 | 基幹で増えたらECにも登録（手動） | ただし掛率・与信が絡み**登録漏れ＝受注不可**。新規取引先の開始前にEC登録する運用ルールを明記 |

### 自動連携でも残る論点

- **EC固有情報（画像・説明文・訴求・検索ワード）は基幹に無い**想定 → 自動連携は基幹項目の生成・更新までで、EC表示用の情報は別途メンテが要る（新パターン発売時に一度整備する運用など）
- 基幹→ECの連携項目（どの項目まで自動で流すか）は要件定義で確定

### 確認したいこと（運用設計用）

1. 基幹の商品データにEC表示に足りる項目がどこまであるか（画像・説明の有無）
2. 価格改定の頻度とタイミング（改定日は事前に分かるか）
3. EC固有情報のメンテ担当（YH／ジョイフルのどちらが、どのタイミングで）

## 出荷実績のEC連携元（8/9整理・ペンディング）

一般論では出荷実績はWMS（倉庫側）→ECが自然。ただしYH回答では倉庫在庫システムは「数量管理のみ」＝**注文と紐づかない在庫台帳の可能性が高く**、注文単位の出荷実績（出荷完了・送り状番号・出荷日）を出せないかもしれない。

| 案 | 内容 | 条件・リスク |
|----|------|--------------|
| A：基幹から | 売上計上＝注文完了をトリガーにECへ | 基幹が送り状番号・出荷日を持つか要確認 |
| **B：倉庫在庫システムから（暫定採用）** | WMS的な一般パターン | 注文紐づけが無ければ**倉庫システム改修が必要**（スコープ拡大） |
| C：EC管理サイトで出荷実績登録 | 物流部／倉庫が管理サイトに出荷登録→EC出荷済み＆基幹へ連携 | 既存システム改修ゼロでPhase1が閉じる。見積の安全策 |

**決定（8/9）**：概略図は暫定Bで記載し、「連携元は要検討」の注記を付ける。CはPhase1初期構成の安全策として提案時に持っておく。

**確認質問（これで決まる）**：出荷実績（注文単位の出荷完了・送り状番号・出荷日）は現状どこに記録されているか。倉庫在庫システムは受注番号と紐づいているか。基幹の売上計上は誰がどのタイミングで入力しているか。
