## 0.5 AS-IS未確定のまま Fit&Gap は出さない

上司指摘: **AS-ISを知らないのにFit&Gapは出せない。**

| やる順 | 内容 |
|--------|------|
| **1（今）** | 資料から読める現状を整理し、先方に「こう理解していますが合っていますか？」 |

資料上のAS-IS（確度高）は主に4点:  
①受注が電話・FAX・メール中心 ②自社出荷とメーカー直送混在で原価手計算 ③取引先別条件の属人化 ④商流 YH→ジョイフル→取引先。  
既存（適合／基幹／WMS／POS／予約）は**名前のみ**。設計書の機能一覧・Phase2/3は**TO-BE**。  

**Phase1の確認の入口**（登場人物・管理者・受注手入力・在庫の正・仕入／POS／マスタ）は  
[ASIS_Phase1_登場人物とシステム.md](./イエローハット_資料/ASIS_Phase1_登場人物とシステム.md) を先に潰す。詳細全体は [ASIS整理_確認用.md](./イエローハット_資料/ASIS整理_確認用.md)。

## 1. 何を求められているか（結論）

**一言**:  
**Phase1**でタイヤ＋その他車用品のBtoB販売をWEB化（見積が欲しい）。  
**Phase2**は空きピット活用の修理・車検予約／依頼。  
**Phase3**は夏冬タイヤ保管のWEB化。  
→ いま欲しいのは **①Phase1の見積 ②Phase2・3はできるかどうか**。

| 項目 | 内容 |
|------|------|
| **Phase1の本命** | タイヤ・その他車用品の**BtoB販売WEB化** |
| **取引先** | 修理工場、ディーラー、**イエローハットFC** など |
| **Phase1の難所** | 送料の**独自ルール**（大半は2本=1口。商品・インチにより1本=1口等もあり） |
| **いまの依頼** | Phase1=見積／Phase2・3=実現可否の回答 |

## 2. 商流・現状の痛み

```
イエローハット（看板・グループ）
    → 子会社 ジョイフル（卸・メーカーベンダー）
        → 取引先（修理工場／ディーラー／YHフランチャイズ 等）
```

公開情報とも整合: 卸強化はジョイフルによる商品開発・新規取引先開拓、との記載あり。

### AS-ISの限界（先方設計書「3つの限界」）※資料根拠あり／詳細は要確認

1. **アナログ受発注** … 電話・FAX・メール → 転記ミス・誤配送・確認工数  
2. **仕入・物流が複雑** … 自社出荷とメーカー直送の混在、欠品時手配、**原価・粗利が手計算**  
3. **取引先別条件の属人化** … 個別掛率・決済・帳票がバックオフィス限界  

打合せ補足: イエローハットの看板で受注できている。  
※「店舗も含めた在庫を見たい」「JAN・適合検索」等は**願望（TO-BE）と現状が混線しやすい**ので、確認リストで切り分ける（→ ASIS整理_確認用）。

## 3. 先方が描くコンセプト

- 自社・メーカー（仕入先）・取引先（店舗／法人／整備工場）と基幹を**共通DBでつなぎ**、  
  **受注 → 在庫引当 → 自動仕入中継 → 売上確定**まで人手を介さず双方向処理  
- BtoB取引先に優位な仕組みで**競合に負けないサービス**→新規開拓・事業拡大  
- タイヤは検索が複雑 → **BtoC機能の流用**を検討したい、との発言あり  

※コンセプトは大きく、**実装はPhase分割で小さく始める**意向（7/22: 1stはシンプルで）。

## 4. フェーズ分け（要望の確定版）

### Phase 1｜タイヤ・その他車用品の販売WEB化 ← **見積対象**

| 項目 | 内容 |
|------|------|
| やりたいこと | タイヤおよびその他車用品の販売をWEB化する |
| 取引先 | 修理工場、ディーラー、イエローハットのフランチャイズ など |
| 送料・口数 | **独自ルール必須**。大半はタイヤ**2本で1口**。商品（インチ等）により **2本=1口／1本=1口** などが変わる |
| 含む想定（既存資料と突合） | 取引先別単価、適合・検索、在庫・納期、見積→注文、工賃・セット、大口CSV、既存連携（段階） |
| フライトへの依頼 | **Phase1の見積** |

### Phase 2｜修理・車検などの予約／依頼WEB化 ← **可否回答**

| 項目 | 内容 |
|------|------|
| やりたいこと | 修理依頼や車検などの予約をWEBでできる仕組み |
| サービス構想 | ディーラーは予約が埋まり依頼を捌けないことがある → **YHの空きピット**があれば依頼を受け、代わりに対応。空きピットを生かした送客・受託 |
| フライトへの依頼 | **できるかどうか**（概算・条件付き可否で可） |

### Phase 3｜タイヤ保管のWEB化 ← **可否回答**

| 項目 | 内容 |
|------|------|
| やりたいこと | 夏冬で履き替えるタイヤの**保管サービスをWEB化**（夏は冬タイヤを預かり、冬は夏タイヤを預かる） |
| フライトへの依頼 | **できるかどうか**（概算・条件付き可否で可） |

```
Phase1 販売WEB（見積） ──→ Phase2 空きピット活用の予約／依頼（可否）
                         └→ Phase3 季節タイヤ保管WEB（可否）
```

## 7. 提案・設計への示唆

| 論点 | 示唆 |
|------|------|
| **提案の出し方** | **Phase1のみ正式見積**。Phase2・3は「できる／条件付きでできる」＋前提・概略工数感 |
| スコープ | Phase1＝タイヤ＋その他車用品のBtoB販売WEB。FC・修理工場・ディーラーが買う側 |
| Mustの核 | ①複数単価 ②在庫・納期 ③適合／JAN検索 ④関連（工賃等）⑤見積→注文 ⑥**インチ／商品別の口数・送料ルール** |
| 難所（Phase1） | 送料ルール表の確定、既存適合・基幹・WMS連携、取寄せ非対応の扱い |
| Phase2可否の見方 | 予約基盤・ピット空きの取得ができれば方向性は実現可。店舗オペ・権限・料金設計が本体 |
| Phase3可否の見方 | 保管そのものは実装可。倉庫ロケ・回送・請求まで含むと別プロダクト級 → 段階提案 |
| リスク | 壮大コンセプトと来春・低予算の矛盾 → Phase1を厚くしすぎない |
| 類比 | TAS（適合・BtoB）、日東おまかせナビ（見積→注文）、チャネル（在庫） |

### Phase1見積スコープ案（社内たたき）

**入れる**: 取引先（修理工場／ディーラー／FC）向け販売、タイヤ＋その他車用品、取引先別単価、適合＋コード検索、在庫・LT、カート、見積→注文、工賃・セット、**商品／インチ別の口数・送料計算**、CSV大口、出荷日指定  
**連携は段階**: マスタ・在庫・受注の必須から  
**見積に含めない（Phase2/3扱い）**: 空きピット振分の本丸、保管WMS、下取り査定本丸  

### Phase2・3の可否回答の型（たたき）

| Phase | 可否の言い方（案） | 条件 |
|-------|-------------------|------|
| 2 | **できる**（予約・振分の仕組みとして） | 既存ピット予約／店舗マスタ連携、溢れた依頼の受付ルール、料金・責任分界 |
| 3 | **できる**（保管サービスWEBとして） | 保管拠点・ロケ運用、入出庫オペ、請求。フルWMSは分割推奨 |
